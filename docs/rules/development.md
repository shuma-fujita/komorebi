# 🌳 GitHub・開発・検証の運用ルール

## 1. 正本と変更時の許可

1. **GitHub `shuma-fujita/komorebi` の `main` がコードの正本。** コードの閲覧・検証はよいが、**ファイルの作成・更新・削除・コミットなどGitHubへの書き込みはユーザーの明示的な許可を得てから**行う。
2. 通常のバックアップ用ブランチを増やさず、変更は小工程でコミットする。検証用の一時ブランチを用いる場合も、長期保存するバックアップと混同しない。
3. **開発入口は `komorebi3d/dev.html`。** 固定Engineの参照、Git履歴、重要資材を無断で変更しない。現時点の変更禁止対象・最新の開発状況は [STATUS.md](../STATUS.md) に記す。
4. **ゲーム開発の正本は `komorebi3d/dev.html`。** 実機PASS済みの状態はGit履歴で管理し、原則としてバックアップ用HTMLを作成しない。`mock.html` は軽量な**UI検証用ページ**であり、安定版・保存用アーカイブではない。

### パネルUI開発の順序と対象範囲

- **パネルUIの開発は、mockで要件定義・表示確認を先行し、ユーザーの承認後に共通UIを `dev.html` へ反映する。**
- **3Dゲーム本体、地図、描画処理などの開発はmock先行の対象外**とし、`dev.html` で直接開発する。
- mockのゲーム表示領域は黒画面とし、3Dエンジンは起動しない。
- ゲームに接続した後の動作確認は `dev.html` で行う。mockでのUI確認とゲーム実機PASSを混同しない。

## 2. 検証結果は混同しない

- **静的チェック／構文チェック／ビルド生成物の一致／模擬ブラウザ試験／GitHub Pages公開版の確認／iPhone・iPad Safari実機PASS**は、対象と確認内容を分けて記録する。
- 未報告の端末別確認、A/B描画、全24配置の網羅検証などを推測でPASSにしない。
- GitHubへのコミット完了と、GitHub Pagesの配信更新・Safariキャッシュ更新は別。表示される「最新コミット」だけで配信ページ自身のSHAが証明されたとは扱わない。

## 3. 作業の継続と記録

- 実機PASS後・方針変更後・チャット移行前には、[STATUS.md](../STATUS.md) の**現在地・未完了タスク**を更新する。完了済み工程の長い時系列は積み増さない。
- **安定的な運用ルールは `docs/rules/` に置く。** `STATUS.md` の定期更新にルール変更を紛れ込ませず、ルール変更時は別途ユーザーと合意する。
- 新しいチャットでは [ルール目次](README.md) と [STATUS.md](../STATUS.md) を読み、必要なGitHub最新ソースを確認して、ユーザーが現在希望する工程から始める。

## 4. 開発情報パネルの更新（緩やかな運用）

- 開発情報の保存先は `komorebi3d/development-info.json`。キーは `engine`（固定Engine SHA）と `forest` / `matsudo` / `common`（それぞれ最新の短い1文）。
- コード変更に合わせて、**該当する区分だけ**情報ファイルを更新する。変更していない区分は保持する。初期値・未登録値は「更新履歴なし」。
- コミットメッセージは更新後の情報ファイルを元に、`forest: ...` / `matsudo: ...` / `common: ...` を行頭に付ける。複数区分を変更した場合は、コミット本文に区分ごとの行を記載してよい。
- 画面の 🆕 は **GitHub main最新コミット**のメッセージにある区分だけに付ける。保存済みの説明が「更新履歴なし」の場合は付けない。GitHub APIが取得できなければ 🆕 は付けず、説明は保存済み情報を表示する。
- 開発情報パネルはページ表示・再読み込み時に取得し、開いたままの定期更新はしない。コミットSHA・日時はGitHub APIから取得し、JSONに複製しない。
- **強制チェック・コミット阻止・専用スクリプトは設けない。** 更新漏れに気づいたら、その時点で修正する。固定Engineには手を加えない。


## 5. 実装完了時の報告形式

Komorebi 3Dの実装完了を報告するときは、毎回以下の3点セットのリンクを表示する。

1. **GitHub Actions**
   - URL: https://github.com/shuma-fujita/komorebi/actions
   - アイコン: GitHub公式の猫ロゴ
2. **ゲーム画面**
   - URL: https://shuma-fujita.github.io/komorebi/komorebi3d/dev.html
   - アイコン: ゲームパッド
3. **モック画面**
   - URL: https://shuma-fujita.github.io/komorebi/komorebi3d/mock.html
   - アイコン: 複数パネルを表すアイコン

### アイコンの固定指定

- GitHub Actions：`favicon`、URL `https://github.com`、サイズ `24px`（GitHub公式の猫ロゴ）。
- ゲーム画面：`icon`、名前 `gamepad-2`、サイズ `lg`。
- モック画面：`icon`、名前 `panels-top-left`、サイズ `lg`。
- 各アイコンと対応するリンクを横並びにする。**絵文字や別のアイコンへ任意に置き換えない。**
- 指定したアイコンを利用できない環境では、別の図柄に置き換えず、リンク名を優先して表示する。

### 表示ルール

- 実装完了報告の最後に、上記の3点セットを表示する。
- 各リンクはアイコンと名称を横並びにする。
- リンクの順序・名称・アイコンを統一する。
- GitHubへの反映、GitHub Actionsの実行結果、実機PASSの確認状況を区別して報告する。
- 未確認のテストをPASSと記載しない。

## 6. 自動テストの追加・維持方針

**自動テストは、人間が実機で確認しきれないことを効率よく検証し、将来も守るべき性質を保護するために使う。テスト数や網羅率そのものを目標にしない。**

### 採用基準
次の3条件を原則すべて満たす場合に限り、追加・維持を検討する。
1. 人間による実機確認では大量・複雑・危険などの理由で十分な検証が難しい。
2. 将来の通常の仕様変更でも維持すべき性質、または外部仕様・データ安全性に関する契約を検証する。
3. 維持コストを上回る具体的なメリットがある。

- 大量の組み合わせ、地図データの欠損・重複・境界、複雑な座標計算、描画データの整合性、保存データ保護、送信先の安全性、構文と生成物の一致を優先する。
- 外観、色、寸法、UI文言・配置、操作感、調整可能な距離・閾値・倍率、キャッシュ文字列、内部実装の書き方は原則として実機確認に任せる。値の妥当性が重要なら、固定値ではなく範囲・単調性・非重複・入力に対する関係などを検証する。
- 製品の現在の出力をそのまま期待値にする、または製品と同じ計算をコピーして正解とするだけのテストは禁止。設定値を使って境界の前後を検証する場合も、期待する性質は独立して定義する。
- ブランド別のテストは増やさず、共通処理の代表例を使う。重複・廃止仕様は整理する。

### 仕様変更・Actions失敗時
- プロダクトコード変更時は関連テストを確認し、必要なら同じ変更で整理する。実行可能な関連テストはコミット前に実行し、できない場合は明示する。
- 失敗時は製品の不具合、テストの不具合、意図した仕様変更、環境の問題を切り分ける。期待値を機械的に変更しない。
- 意図した仕様変更で失敗したテストは上の3条件から再評価し、価値が低ければ削除・実機確認に移行する。必要な契約なら変更理由を明示し期待値を修正する。
- テストを通すためだけに製品仕様を戻さない。安全性・データ保護の検証を失敗回避目的で無効化しない。
- 固定Engineのテストは変更しない。自動テストの成功と実機PASSを混同しない。
